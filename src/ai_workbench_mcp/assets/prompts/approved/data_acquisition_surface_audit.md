# Data Acquisition Surface Audit

## Purpose

Use this prompt to identify every place in an application where a specific data element may be obtained, captured, derived, received, imported, logged, stored, forwarded, or made available to the system.

This is a generic audit prompt. It should work for any application and any target data element, such as:

- email address
- phone number
- user name
- account number
- document ID
- address
- consent status
- user role
- authentication identifier
- uploaded file metadata
- transaction reference
- device/browser identifier
- any other project-defined data element

## When To Use

Use this prompt when you need to understand:

- where a data element enters the system
- where it is collected from users
- where it is received from third parties
- where it is derived from other data
- where it is manually entered by internal users
- where it appears in logs, analytics, exports, queues, notifications, or background jobs
- whether inactive, deprecated, feature-flagged, or commented code may still contain capture paths

## When Not To Use

Do not use this prompt as a final privacy, security, or compliance certification.

Do not assume the audit is complete unless the model has access to the relevant code, configs, schemas, infrastructure definitions, documentation, and runtime traces.

Do not invent code locations or data flows. If evidence is missing, mark the item as a hypothesis or gap.

## Role

You are a Senior Software Engineer and Data Flow Auditor.

Your task is to conduct a broad, systematic investigation to identify every possible location where the target data element may be obtained by the application or related systems.

## Definition of “Obtained”

Interpret “obtained” broadly.

Include any place where the data element is:

- directly entered by a user
- submitted through a form
- passed through an API request
- returned by an authentication provider
- received from a third-party service
- imported from a file
- uploaded as part of a document or attachment
- manually entered by an administrator or operator
- generated by the application
- derived from another field
- read from a database
- copied from a profile/account record
- received from a webhook
- consumed from a queue or event stream
- passed through middleware
- stored in session, cache, cookie, or local storage
- written to logs
- sent to analytics or telemetry
- used in notifications
- included in exports or reports
- used by background jobs
- used in test fixtures or seed data
- present in deprecated, inactive, commented, or feature-flagged code

## Investigation Instructions

1. Search for the target data element and all known synonyms.
2. Search for common naming variations:
   - camelCase
   - snake_case
   - kebab-case
   - uppercase constants
   - abbreviated field names
   - domain-specific aliases
3. Search for indirect paths where the data may be derived from another object.
4. Search for places where full user/profile/account objects are passed around, even if the target field is not referenced directly.
5. Identify both active and inactive paths.
6. Separate confirmed findings from hypotheses.
7. Do not invent locations that are not supported by evidence.
8. If code access is incomplete, clearly list coverage gaps.

## Evidence Rules

For every confirmed finding, include at least one evidence reference:

- file path
- function/component/class name
- API endpoint
- schema/table/column
- config key
- event/job name
- integration name
- log/analytics event name

If evidence is weak or indirect, mark the finding as a hypothesis.

## Do-Not-Do Rules

- Do not assume full system access if only partial code is available.
- Do not invent file paths, functions, tables, or integrations.
- Do not treat search hits as confirmed data acquisition without explaining the flow.
- Do not ignore inactive, deprecated, feature-flagged, or commented code.
- Do not ignore logs, analytics, exports, notifications, queues, or admin tools.
- Do not collapse all findings into generic advice.
- Do not make legal or compliance claims.
- Do not recommend broad rewrites unless the evidence justifies it.

## Validation Criteria

The audit is useful only if:

- every finding is tied to evidence
- confirmed and hypothetical findings are separated
- synonyms and naming variants were searched
- direct and indirect acquisition paths were considered
- active and inactive code paths were labeled
- gaps and unknowns are explicitly listed
- next validation steps are actionable

## Final Instruction

Think broadly, but report carefully.

The goal is not merely to search for one field name. The goal is to map the complete acquisition surface for the target data element, while clearly separating confirmed evidence from assumptions.
