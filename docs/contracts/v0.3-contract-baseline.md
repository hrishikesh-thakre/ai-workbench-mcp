# v0.3 Contract Baseline

Status: v0.3 semantic PR acceptance alpha contract baseline, not v1-stable

This document records the v0.3 alpha contract for Workbench run evidence,
policy-pack metadata, and the GitHub PR acceptance surface. It extends the
v0.2 baseline without making the contracts v1-stable.

Workbench acceptance still requires deterministic validation plus a quality-gate
decision. A green CI run, MCP response, uploaded artifact, sticky PR comment, or
scaffold validation folder is not enough by itself.

## Compatibility Rules

- `schema_version` remains `1` where an artifact or response envelope includes
  it.
- Consumers must tolerate additive fields and unknown reason codes.
- Consumers must tolerate v0.2 committed sample runs that omit additive fields
  such as `schema_version`, `policy_pack`, `reason_sources`, and `reason_codes`.
- Paths in public artifacts should be repo-relative or artifact-relative.
- Do not publish local absolute paths, provider secrets, private run history,
  raw provider logs, or unreviewed `runs/` contents.
- `runs/<run_id>/` remains the local evidence ledger and stays ignored by git.
  Committed examples belong under `examples/sample-runs/` or sanitized proof
  fixtures under `examples/pr-gate-outcomes/`.

The v0.2 baseline remains the compatibility reference for older sample evidence:
[`v0.2-contract-baseline.md`](v0.2-contract-baseline.md).

## Complete Run Evidence

A complete Workbench acceptance run normally contains:

```text
runs/<run_id>/
  task_metadata.json
  final_prompt.md
  model_selection.json
  model_output.md
  validation_report.json
  revision_decision.json
  run_log.jsonl
```

Optional evidence can include `events.jsonl`, `model_call_metadata.json`, review
prompts, review outputs, second-pass artifacts, generated analytics reports, and
local dashboards.

A run is accepted only when:

- `validation_report.json` has `overall_status="passed"`.
- `validation_report.json` has `sign_off_ready=true`.
- `revision_decision.json` has `final_status="accepted"`.

`workbench_analyze_runs --evidence-scope complete` counts only child folders
with `run_log.jsonl`, `validation_report.json`, and
`revision_decision.json`. Missing required artifacts are reported in
`excluded_runs_by_reason`.

## validation_report.json

`validation_report.json` is written by `workbench_validate_run` /
`tools/validate_run.py`.

Current writer fields:

- `schema_version` when emitted by the current writer
- `run_id`, `project`, `profile`, `generated_at`
- `commands_run`: command result objects with `name`, `command`, `cwd`,
  `required`, `weight`, `exit_code`, `status`, and `duration_ms`
- `commands_not_run`: skipped command objects with `name` and `reason`
- `artifact_checks` and `review_checks`: check objects with `name`, `status`,
  `summary`, `details`, and `reason_codes`
- `missing_context_notes`
- `overall_status`: `passed`, `needs_review`, or `failed`
- `sign_off_ready`
- `confidence`
- `summary`: command and check counts
- `policy_pack`: `name`, `version`, and optional `source` when the selected
  profile resolves first-class policy metadata
- `profile_source`, `reason_sources`, `reason_codes`, and
  `detailed_confidence` when available

`reason_sources` entries use:

```text
code
status
severity
source
name
summary
details
```

`severity="blocker"` is the machine-readable signal downstream PR surfaces use
to block even when a higher-level status says review is required.

Older v0.2 sample runs can omit `schema_version`, `policy_pack`,
`reason_sources`, and `reason_codes`. Consumers should fall back to
`overall_status`, `sign_off_ready`, command results, and check results.

## revision_decision.json

`revision_decision.json` is written by `workbench_quality_gate` /
`tools/quality_loop.py`.

Current writer fields:

- `schema_version` when emitted by the current writer
- `generated_at`
- `loop_type`
- `required`
- `reason`
- `next_action`
- `accepted_pass`
- `final_status`: usually `accepted`, `review_required`, or
  `revision_required`
- `authoritative_model_output`
- `authoritative_validation_report`
- `first_pass_artifacts` and `second_pass_artifacts` when a loop compares
  multiple passes
- `blocking_findings` and `non_blocking_findings`
- `reason_sources` and `reason_codes`

Older accepted examples may omit additive reason fields. Consumers should fall
back to `final_status`, `reason`, `next_action`, and finding lists when reason
metadata is absent.

## Policy-Pack Catalog

The v0.3 first-class policy-pack catalog lives at
`configs/policy_packs.yaml`.

The catalog top-level shape is:

```text
schema_version: 1
policy_packs:
  <policy_pack_name>:
    name: <policy_pack_name>
    version: v0.2
    allowed_files: [...]
    required_tests: [...]
    required_evidence: [...]
    review_triggers: [...]
    blocker_rules: [...]
    reason_codes:
      accepted: <code>
      required_test_missing: <code>
      required_test_failed: <code>
      required_tests_passed: <code>
```

The product catalog must define exactly these five policy packs:

- `docs_only`
- `low_risk_bug_fix`
- `test_fix`
- `api_contract_change`
- `security_privacy_sensitive`

The loader normalizes each pack with `name`, `version`, `source`,
`allowed_files`, `required_tests`, `required_evidence`, `review_triggers`,
`blocker_rules`, and `reason_codes`.

Validation profiles keep their existing names and continue to be the recipe
selection surface. Product profiles reference catalog entries through
`policy_pack.name`; support profiles can omit first-class policy metadata. The
catalog does not replace deterministic validation or quality-gate acceptance.

## PR Decision JSON

The PR gate renderer writes:

```text
runs/pr_gate/pr_comment.md
runs/pr_gate/pr_decision.json
```

`pr_decision.json` fields:

- `schema_version`
- `operation`: `workbench_pr_gate`
- `outcome`: exactly one of `accept`, `needs_review`, or `block`
- `ok`
- `run_id`
- `evidence_source`: `acceptance_run`, `fallback_scaffold`, or `missing`
- `source_run_dir`
- `validation_status`
- `quality_gate_status`
- `reason`
- `reason_codes`
- `evidence`: entries with `label`, `path`, and `present`
- `required_next_action`

Standard evidence labels and paths are:

```text
validation_report -> validation_report.json
revision_decision -> revision_decision.json
model_output -> model_output.md
run_log -> run_log.jsonl
```

Decision mapping:

- `accept`: validation passed, `sign_off_ready=true`, and the quality gate
  accepted the run.
- `needs_review`: validation or quality gate requires review and no
  blocker-severity reason source exists.
- `block`: missing or unreadable required evidence, failed validation, revision
  required, blocker-severity reason source, unknown acceptance state, or
  scaffold-only fallback evidence.

Scaffold-only fallback evidence always blocks with reason code
`pr_gate.acceptance_evidence_missing`.

The PR gate can accept v0.2 sample runs when the required validation and quality
fields are present, even if additive v0.3 reason metadata is absent.

## PR Comment Surface

The Markdown PR comment is a scan-first surface. The first lines answer:

```text
# AI Workbench PR Gate: Accept|Needs Review|Block

Decision: Accept|Needs Review|Block
Why: <reason>
Required next action: <required_next_action>
Evidence present: validation_report yes|no, revision_decision yes|no
```

The comment also includes:

- run id, evidence source, and source run dir
- validation and quality-gate status table
- evidence artifact table
- reason code list
- a hygiene note that raw model output and provider logs are not embedded

`tools/pr_gate_comment.py` prepends the sticky marker before posting:

```text
<!-- ai-workbench-pr-gate -->
```

The marker comment is a presentation surface only. It is not a substitute for
`validation_report.json` and `revision_decision.json`.

## GitHub Workflow Template Boundary

The reusable workflow template lives at:

```text
.github/workflows/ai-workbench-pr-gate.yml
```

The template:

- installs `ai-workbench-mcp==0.2.0a0` by default
- accepts an explicit `workbench_run_dir`, or `workbench_runs_dir` plus
  `workbench_run_id`
- falls back to `workbench_fallback_run_dir` only when no real run directory is
  available
- renders `runs/pr_gate/pr_comment.md` and `runs/pr_gate/pr_decision.json`
- uploads those files as the `workbench-pr-gate` artifact
- posts or updates one marker-based sticky PR comment for same-repository pull
  requests
- skips sticky comment posting for fork pull requests

The template does not run Goose, create a Workbench run, replace the evidence
artifacts, treat CI status as acceptance, call the GitHub Checks API, or define
merge enforcement policy.

## Package And Bootstrap Boundary

The latest published PyPI package remains `ai-workbench-mcp==0.2.0a0` until a
future release is explicitly shipped.

The source tree now carries bootstrappable repo assets under
`src/ai_workbench_mcp/assets/`:

- `configs/`, including `policy_packs.yaml`
- `prompts/approved/`
- `recipes/`

Installed-package users can materialize those defaults with:

```bash
python -m ai_workbench_mcp.tools.bootstrap_assets --target-dir .
ai-workbench-bootstrap-assets --target-dir .
```

The bootstrap command writes repo-style assets and leaves existing files
untouched unless `--force` is supplied. The package and bootstrap boundary does
not include private `runs/` evidence, committed proof fixtures, provider setup,
or a claim that v0.3 has been published to PyPI.

## Deliberately Not Stable Yet

The following surfaces remain provisional until a later v1 contract pass:

- exact reason-code catalog and policy-pack expansion rules
- dashboard visual structure and CSS
- routing feedback thresholds and model-selection policy changes
- provider-specific cost metadata beyond the currently documented optional
  fields
- GitHub Checks API integration, merge enforcement behavior, and fork-comment
  strategy
- Codex cloud evidence export and persistence
