# v0.2 Contract Baseline

Status: v0.2 alpha contract baseline, not v1-stable

This document records the current public contract shapes after the v0.2 policy, reason-code, analytics, dashboard, and PR gate passes. It is a baseline for downstream hosts and CI integrations, not a promise that these contracts are frozen for v1.0.

Workbench acceptance still requires deterministic validation plus a quality-gate decision. A green CI run, successful MCP call, generated dashboard, or PR comment is never enough by itself.

## Compatibility Rules

- `schema_version` is `1` where an artifact or response envelope includes it.
- Consumers must tolerate additive fields.
- Consumers must tolerate older committed sample runs that omit newer additive fields such as `policy_pack`, `reason_sources`, and `reason_codes`.
- Paths in public artifacts should be repo-relative or artifact-relative. Do not publish local absolute paths, provider secrets, private run history, raw provider logs, or unreviewed `runs/` contents.
- `runs/<run_id>/` remains the local evidence ledger and stays ignored by git. Committed examples belong under `examples/sample-runs/`.

## Run Folder Evidence

A complete Workbench acceptance run normally contains:

```text
runs/<run_id>/
  task_metadata.json
  final_prompt.md
  model_selection.json
  model_output.md
  validation_report.json
  revision_decision.json
  run_log.jsonl
```

`events.jsonl`, `model_call_metadata.json`, review prompts, review outputs, second-pass artifacts, and generated analytics reports are optional evidence.

A run is accepted only when:

- `validation_report.json` has `overall_status="passed"`.
- `validation_report.json` has `sign_off_ready=true`.
- `revision_decision.json` has `final_status="accepted"`.

`workbench_analyze_runs --evidence-scope complete` counts only child folders with `run_log.jsonl`, `validation_report.json`, and `revision_decision.json`. Missing artifacts are reported in `excluded_runs_by_reason`.

## Validation And Quality Gate

`validation_report.json` is written by `workbench_validate_run` / `tools/validate_run.py`.

Current writer fields:

- `run_id`, `project`, `profile`, `generated_at`
- `commands_run`: list of command results with `name`, `command`, `cwd`, `required`, `weight`, `exit_code`, `status`, and `duration_ms`
- `commands_not_run`: list of skipped command objects with `name` and `reason`
- `artifact_checks` and `review_checks`: check objects with `name`, `status`, `summary`, `details`, and `reason_codes`
- `missing_context_notes`
- `overall_status`: `passed`, `needs_review`, or `failed`
- `sign_off_ready`
- `confidence`
- `summary`: command/check counts
- `policy_pack`: `name` and `version` when the selected profile declares policy metadata
- `profile_source`, `reason_sources`, `reason_codes`, and `detailed_confidence`

`reason_sources` entries use:

```text
code
status
severity
source
name
summary
details
```

`severity="blocker"` is the machine-readable signal downstream PR surfaces use to block even when a higher-level status says review is required.

`revision_decision.json` is written by `workbench_quality_gate` / `tools/quality_loop.py`.

Current writer fields:

- `generated_at`
- `loop_type`
- `required`
- `reason`
- `next_action`
- `accepted_pass`
- `final_status`: usually `accepted`, `review_required`, or `revision_required`
- `authoritative_model_output`
- `authoritative_validation_report`
- `first_pass_artifacts` and `second_pass_artifacts`
- `blocking_findings` and `non_blocking_findings`
- `reason_sources` and `reason_codes`

Older accepted examples may omit the additive reason fields. Consumers should fall back to `final_status`, `reason`, and finding lists when reason metadata is absent.

## Policy Profiles

v0.2 policy packs live inside `configs/validation_profiles.yaml` as validation profile metadata. There is no separate policy-pack package or directory yet.

A validation profile can declare:

- `description`
- `commands`
- `required_artifacts`
- `non_empty_artifacts`
- `review_checks`
- `consistency_checks`
- `changed_file_policy`
- `task_test_command`
- `policy_pack`

`policy_pack` can declare:

- `name`
- `version`
- `allowed_files`
- `required_tests`
- `required_evidence`
- `review_triggers`
- `blocker_rules`
- `reason_codes`

The current core product profiles are `docs_only`, `low_risk_bug_fix`, `test_fix`, `api_contract_change`, and `security_privacy_sensitive`. Additional v0.2 profiles such as `low_risk_coding`, `python_package_maintenance`, `fixture_repair_proof`, `tiny_python_fix`, `run_signoff`, and `scaffold` support demos, package maintenance, and self-validation.

The exact reason-code catalog is still provisional. Consumers should display unknown reason codes rather than reject them.

## MCP Response Envelope

All six MCP tool wrappers return the shared Workbench response envelope:

```json
{
  "schema_version": 1,
  "operation": "workbench_<operation>",
  "status": "operation-specific status",
  "ok": true,
  "artifacts": {},
  "summary": {},
  "errors": []
}
```

Registered MCP tools:

- `workbench_open_run`
- `workbench_select_model`
- `workbench_record_execution`
- `workbench_validate_run`
- `workbench_quality_gate`
- `workbench_analyze_runs`

`artifacts` values are JSON-safe paths. `summary` is operation-specific and should be treated as a compact index, not a replacement for the underlying artifact. `errors` contains objects with at least `code` and `message` when `ok=false`.

Core operations append best-effort `events.jsonl` entries when possible. Event write failures are non-fatal and must not change the core response result.

## Analytics And Dashboard

`workbench_analyze_runs` writes:

- `run_metrics.json`
- `run_summary.md`
- `run_dashboard.html`

Key `run_metrics.json` fields:

- `evidence_scope`, `excluded_runs_total`, `excluded_runs_by_reason`
- `runs_total`, `runs_passed`, `runs_failed`, `runs_needs_review`
- `accepted_runs_total`, `review_required_runs_total`, `failed_runs_total`, `outcome_counts`
- `accepted_runs_by_recipe`, `accepted_runs_by_execution_host`, `accepted_runs_by_response_source`
- `execution_host_counts`, `response_source_counts`
- `quality_gate_outcomes`, `failure_reasons`, `outcome_breakdown`
- `routing_feedback_candidates`
- `cost_tracking`, `time_tracking`, and `run_cost_time`

Cost and time evidence is optional. Missing values mean evidence was not recorded, not that a run was free or instantaneous.

`run_dashboard.html` is a generated local report. It links to evidence artifacts by relative path and does not embed raw model output or provider logs. Its visual markup and CSS are not stable API.

## PR Gate Artifacts

`tools/pr_gate.py` writes:

```text
runs/pr_gate/pr_comment.md
runs/pr_gate/pr_decision.json
```

`pr_decision.json` fields:

- `schema_version`
- `operation`: `workbench_pr_gate`
- `outcome`: `accept`, `needs_review`, or `block`
- `ok`
- `run_id`
- `evidence_source`: `acceptance_run`, `fallback_scaffold`, or `missing`
- `source_run_dir`
- `validation_status`
- `quality_gate_status`
- `reason`
- `reason_codes`
- `evidence`: entries with `label`, `path`, and `present`
- `required_next_action`

Decision mapping:

- `accept`: validation passed, `sign_off_ready=true`, and quality gate accepted.
- `needs_review`: validation or quality gate requires review and no blocker-severity reason source exists.
- `block`: missing or unreadable required evidence, failed validation, revision required, blocker-severity reason source, or scaffold-only fallback evidence.

Scaffold-only fallback evidence blocks with reason code `pr_gate.acceptance_evidence_missing`.

The Markdown PR comment artifact includes:

- title: `AI Workbench PR Gate: Accept|Needs Review|Block`
- run id, evidence source, source run dir, reason, and required next action
- validation and quality-gate status table
- evidence artifact table
- reason code list
- a hygiene note that raw model output and provider logs are not embedded

`tools/pr_gate_comment.py` prepends the sticky marker before posting:

```text
<!-- ai-workbench-pr-gate -->
```

The GitHub workflow posts or updates one marker comment only for same-repository pull requests. Fork pull requests still render and upload the artifacts but skip comment posting.

## Deliberately Not Stable Yet

The following surfaces remain provisional until a later v1 contract pass:

- exact reason-code catalog and policy-pack expansion rules
- first-class policy-pack directory/package format
- dashboard visual structure and CSS
- routing feedback thresholds and model-selection policy changes
- provider-specific cost metadata beyond the currently documented optional fields
- GitHub Checks API integration, enforcement behavior, and fork-comment strategy
- Codex cloud evidence export and persistence
